2. Stärkster Differenzierungspunkt

Wesensunterschied: Die meisten Portfolios zeigen „es läuft“. Dieses Portfolio zeigt, wie man das „es läuft“ in einem geregelten Entwicklungsprozess belegen kann — mit deterministischen Fault-Injection- Szenarien, reproduzierbaren Evidence-Logs, automatisiertem Coverage-Gate und einer ASPICE-Traceability. Das ist genau die Denkweise, die deutsche Tier-1 und OEM im Interview abfragen („Wie weißt du, dass dein Code das tut, was er soll?“).

3. Belege (evidence/)

  • Determinismus: Jeder Szenario-Lauf erzeugt eine identische Zeile im Trace (z. B. SEC_TIMEOUT 500-ok) — wiederholbar per make evidence.
  • WdgM-Recovery: evidence/wdgm-recovery.log zeigt FAILED → OK (EXIT_CODE 0) nach Alive-Supervision-Dropout.
  • UDS: evidence/uds.log / evidence/uds-dtc.log dokumentieren ReadDataByIdentifier (0x22) und ReadDTCInformation (0x19).
  • NvM: evidence/uds-dtc.log mit DTC 0x080150 (VehicleSpeed / softDTC, Status 0x50) — CRC16-gesichert + redundanter Block.
  • Testbericht: evidence/test-report.md (27 Tests, 0 Fehler).

5. Diese Stärken BEWEISEN (fürs Vorstellungsgespräch)

  • „Warum WdgM?“ → Alive-Supervision deckt nicht nur den CAN-Timeout, sondern die Lebensaktivität des Kommunikationsstacks ab — Trennung von „Signal weg“ vs. „Signal falsch“ (Zweigentscheidung im Code).
  • „Warum NvM CRC?“ → CRC16-CCITT (0x1021) pro Block + redundanter Speicherblock: Fehlererkennung UND Redundanz sind getrennte Methoden — genau das Argument eines Safety-Integritätsdesigns.
  • „Woher weißt du, dass es testbar ist?“ → 11 deterministische Fault-Injection-Szenarien, jede mit Exit-Code-Gate; Reproduzierbarkeit ist Gate-Bedingung (make coverage).
  • „Woher die Coverage-Zahl?“ → llvm-cov report über alle 10 Szenarien-Läufe gemerged: 100 % Zeilen, 92 % Zweige (Min-Gate 80 %).
  • „Was ist der Unterschied zu CANoe/Canape-Captures?“ → Diese halten «BUS-Bewegung» fest; dieses Portfolio hält BSW-Evidenz + Prozessnachweis + deterministische Fehlerpfade fest.
